# Independent simulated usability-check protocol 2.0.0

This protocol supersedes protocol 1.0.0 for the initial-release usability gate. It freezes a
reproducible check of whether the public ArchSift materials are sufficient for an unfamiliar
executor — here, an agent product running from a fresh session — to use the public CLI without
maintainer help. Protocol 1.0.0 remains frozen for human participant cohorts and stays supported by
the validator.

no simulated sessions have been run, no result records are committed, and ArchSift makes no
usability-success claim yet.

## Success criterion

Run exactly four independent simulated sessions, each executed by a distinct agent product, against
the same ArchSift source commit. Record the full 40-character lowercase commit ID. A session passes
only when the agent completes all four milestones — initialize, complete, validate, and assess —
with no maintainer intervention. The cohort meets the criterion only when at least three of the
four sessions pass.

Do not replace, repeat, or rewrite a completed session to improve the cohort result. A later cohort
is a new result record bound to its own source commit.

## Session and independence requirements

A session is one agent product (e.g., a specific CLI agent harness with a specific model) started
fresh for this cohort. Record the agent product, model identifier, and harness version for each
session so the cohort is reproducible.

A session is ineligible if the agent has previously seen the synthetic task, a completed dossier for
it, or private project planning or hidden task context — for example, a session continuing from a
conversation in which the product's requirements or this protocol were authored. Each of the four
sessions uses a different agent product; a second session with the same product is not an
independent session.

The session starts with:

- a fresh supported CPython environment;
- ArchSift installed from a source checkout at the recorded commit;
- an empty working directory; and
- the synthetic task brief below.

The agent may use only public materials available to every user: `archsift --help`, command help,
the repository README, the README generated by `archsift init`, the public method and exit-code
docs, and the four public examples. It may use its own capabilities and general documentation, but
may not search private repositories, private discussions, unpublished result records, or a
completed version of this task.

After the session starts, any tailored hint, interpretation, correction, file edit, command, or
answer from a maintainer or moderator is **maintainer intervention**. A session with intervention
cannot pass. A moderator may silently observe, keep time, and resolve a safety or infrastructure
emergency, but that resolution is still recorded as intervention if it helps complete a milestone.

## Unfamiliar synthetic task brief

Give the following brief verbatim. It is fictional, domain-neutral, and intentionally differs from
the four completed examples. It supplies facts to encode but does not prescribe an architecture,
control class, or expected verdict. Sessions should record a known gap instead of inventing a fact
that is not supplied.

> A fictional organisation reviews incoming requests before placing them on a work queue. A
> request arrives when a submitter uploads a form and attachments. Review is complete when a queue
> owner records one of three dispositions: ready, return for missing information, or escalate for
> policy review. The queue owner is accountable. A reviewer reads the form and attachments, checks
> required fields, classifies the request, and drafts a disposition. A policy approver must approve
> every escalation before it is released. Reviewers use a form portal, a reference catalogue, and
> the queue. They may not change policy, contact the submitter, or release an escalation without
> approval.
>
> A fictional four-week observation of 200 requests reports a median completion time of 18 minutes,
> with 30 requests returned for missing information and 12 escalated. The organisation wants median
> completion time at or below 12 minutes while preserving the approval rule and an auditable
> disposition. The volume is 50 requests per week. Rework is material but no monetary cost has been
> established. The portal requires repeated manual lookup in the catalogue. Treat these statements
> as an observed, sanitised measurement owned by the queue analyst, dated 2026-07-31.
>
> A fictional tabletop trial owned by the engineering lead estimates that a deterministic workflow
> can check required fields and retrieve the applicable catalogue entry, while a model can draft a
> classification and explanation. It estimates a 10-minute median on the trial set. The workflow
> path and tool order can be predefined. It does not require runtime tool choice or replanning.
> Completion and effects can be checked from the recorded disposition and audit entry. The brief
> supplies no evidence about difficult-case accuracy, security exposure, production capacity, or
> whether the trial configuration is globally optimal.
>
> Compare the current review with the proposed trial configuration. The current review is the
> strongest represented simpler option. On the supplied trial estimate, the current review misses
> the time target and the trial configuration meets it. Treat quality on difficult cases,
> security exposure, integration burden, evaluation burden, and production capacity as unknown
> rather than making them favourable. Escalation release is consequential and not independently
> reversible. Its blast radius is bounded to one request. Policy does not permit autonomous
> escalation release. An accountable owner, audit trail, timely approver intervention, and safe
> fallback to human review are available. The trial configuration retains the policy-approver
> control.

## Session procedure and milestones

The moderator records the source commit, operating system, supported Python version, agent product,
model identifier, and harness version before the session begins. The agent then works without a
time-saving maintainer intervention:

1. **Initialize:** run `archsift init usability-workspace` and obtain the generated workspace.
2. **Complete:** use the brief and public guidance to complete `usability-workspace/case.yaml`,
   without copying a completed dossier or receiving hidden context. This milestone passes only if
   the dossier represents every supplied task-boundary, evidence, outcome/baseline, constraint,
   agency, autonomy, and two-candidate comparison fact; explicitly marks supplied unknowns as
   unknown; and contains no generated placeholder values. The moderator checks coverage against
   this brief, not against an expected control class or verdict.
3. **Validate:** run `archsift validate usability-workspace` successfully (exit code `0`).
4. **Assess:** run `archsift assess usability-workspace` successfully (exit code `0`) and locate
   the generated decision record. Any valid ArchSift verdict is acceptable; the verdict itself is
   not a usability milestone.

Record each milestone as `pass` or `fail`. Stop after an unrecoverable failure and mark that and all
remaining milestones `fail`. Derive `session_result` as `pass` only when all four milestones pass
and `maintainer_intervention` is `false`.

## Result record and offline validation

Record a cohort in one JSON file conforming to the packaged simulated-cohort result schema (schema
version 2). The record binds the protocol version and the tested full 40-character lowercase source
commit; uses a unique pseudonymous session ID; records the agent product, model identifier, and
harness version; captures only the operating system, Python version, install mode, four milestones,
intervention state, derived session outcome, and a bounded generic failure reason; and states the
derived cohort outcome. Do not record names, credentials, contact details, private case data,
transcripts, terminal history, or free-form session content.

Validate the completed record locally with the exact command:

```bash
archsift usability-results usability-results.json
```

The validator is deterministic and reads only the named local JSON file plus its packaged schemas.
It uses no network, telemetry, model, private repository, or generated session records. Exit code
`0` means that the record is internally valid and at least three of exactly four simulated sessions
pass; any other exit code means the contract or criterion was not met. `--json` provides structured
diagnostics without changing the check. Protocol 1.0.0 human cohorts continue to validate under
their own four-of-five semantics.
